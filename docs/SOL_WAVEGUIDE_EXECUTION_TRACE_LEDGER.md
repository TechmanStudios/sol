# SOL Waveguide Execution Trace Registry / Rejection Ledger

This document defines the Execution Trace Registry / Rejection Ledger system, outlining how it compiles and indexes individual governed execution/rejection records, schema specifications, validation constraints, and hashing strategies.

---

## 1. Purpose of the Trace Ledger

The Execution Trace Registry / Rejection Ledger collects individual execution and rejection records generated by the Governed Pass Execution Harness and indexes them into a canonical, deterministic, auditable ledger:

```text
Governed Pass Execution Harness
→ Execution Trace Registry / Rejection Ledger
→ future Governed Pass Replay Verifier
```

It tracks exactly which compiler passes executed successfully, which passes were rejected (and why), and collects the digests of input and output payloads to enable downstream auditability and replays.

---

## 2. Trace Entry and Top-Level Ledger Schemas

### Trace Entry Schema
*   `trace_entry_id`: Canonical trace entry identifier (e.g. `SOL-WAVEGUIDE-TRACE-ENTRY-RC1-pipeline_compaction-FULL_SAFE_OPTIMIZED`).
*   `rc_id`: Release Candidate ID (`SOL-WAVEGUIDE-RC1` or `SOL-WAVEGUIDE-RC2`).
*   `candidate_level`: Level of the candidate (`foundation` or `governed_execution_stack`).
*   `requested_pass` / `requested_profile`: Details of requested compiler pass.
*   `execution_status`: Status of the execution record (`trace_executed`, `trace_rejected`, `trace_warning`, or `trace_invalid`).
*   `admission_status`: Admission status copied from the decision.
*   `admission_decision_digest`: Reference to the admission decision digest.
*   `execution_record_path`: Path to the raw execution record JSON file.
*   `execution_record_digest`: Reference to the execution record digest.
*   `handler_id` / `handler_version` / `handler_registered`: safe handler details.
*   `input_payload_digest` / `output_payload_digest`: reference payload digests.
*   `pass_executed` / `pass_rejected`: Boolean indicators.
*   `reason_codes`: Sorted list of evaluation reason codes.
*   `notes`: Explanatory details.
*   `software_validation_caveat`: Inherited caveat showing shadow sandbox simulation context.
*   `trace_entry_digest`: SHA256 digest of key-sorted trace entry JSON (excluding `trace_entry_digest` itself).

### Top-Level Ledger Schema
*   `ledger_id`: Canonical ledger identifier (`SOL-WAVEGUIDE-EXECUTION-TRACE-LEDGER`).
*   `ledger_version`: Ledger version string (`1`).
*   `ledger_status`: Verification status (`ledger_valid`, `ledger_blocked`, or `ledger_warning`).
*   `entries`: Sorted list of all compiled trace entries.
*   `executed_entries` / `rejected_entries` / `invalid_entries`: Filtered subsets.
*   `executed_count` / `rejected_count` / `invalid_count`: Counter metrics.
*   `rc1_execution_count` / `rc2_execution_count` / `rc1_rejection_count` / `rc2_rejection_count`: Level counter metrics.
*   `approved_handler_ids`: Sorted, unique list of handler IDs included in the ledger.
*   `artifact_paths`: Sorted, unique list of raw execution record paths.
*   `source_execution_record_digests`: Sorted, unique list of raw execution record digests.
*   `software_validation_caveat`: Proves sandbox validation context.
*   `reason_codes`: Top-level validation codes.
*   `ledger_digest`: SHA256 digest of key-sorted ledger JSON (excluding `ledger_digest` itself).

---

## 3. Entry Sorting Strategy

To ensure deterministic compilation, the top-level ledger sorts all child entries by:
1.  `rc_id`
2.  `requested_pass`
3.  `requested_profile`
4.  `execution_status`
5.  `execution_record_digest`

---

## 4. Validation Rules

### Trace Entry Validation
A trace entry is valid only when:
*   The raw execution record validates successfully.
*   The raw execution record digest matches the recorded digest.
*   For executed traces: `pass_executed` is `true`, handler metadata is present, and input/output digests are present.
*   For rejected traces: `pass_rejected` is `true`, rejection reasons are present, and there is no handler execution claim.

### Top-Level Ledger Validation
The ledger is valid only when:
*   All child entries validate successfully.
*   All counter metrics match the entries' properties.
*   All top-level helper lists (approved handlers, digests, paths) are sorted and unique.
*   No invalid entry is silently accepted.

---

## 5. Hashing Specifications

Uses canonical JSON serialization and key-sorting:
*   Uses **SHA256** canonical hashing.
*   Self-referential digest fields (`trace_entry_digest` on entries and `ledger_digest` on the ledger) are stripped before hashing.
